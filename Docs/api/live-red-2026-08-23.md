# The live suite is red — what changed API-side (2026-08-23)

Probe branch `probe/live-red`, cut from `main` (`5c01c68`). Nothing merged,
nothing in the app or in any spec was modified. `scripts/api-sweep.mjs` was
lifted unchanged from `chore/api-sweep` (`89199d9`) — md5 `7bb47b3…` both
sides — and run against the deployed API with `LIVE_MEDIA` unset.

## Verdict

1. **Nothing about the contract changed.** 118 operations, **118 ok, 0
   mismatches**, byte-identical to the 2026-08-19 baseline: same statuses, same
   wallet (`5000/0/5000`), no operation added or missing. No 429, no `Retry-After`,
   no 5xx, no request that was never sent, anywhere — in the sweep or in four
   captured signup→wizard walks (64 calls, all 200/201). Code `000000` is still
   accepted (`POST /auth/verify-email` → 200, every time).
2. **What changed is the latency TAIL, not the median.** Same 118 calls:
   116.1 s of wall time on 2026-08-19, **410.3 s today** — 3.5×. The median
   barely moved; the number of multi-second stalls did.
3. **The walk was never comfortably green.** On the baseline day the
   wizard-Finish burst summed to **24,503 ms against a 25,000 ms budget** —
   497 ms of headroom. It only ever passed because nothing stalled.

## It is cold starts, not throttling

Measured directly against `/health`:

```
12 back-to-back:  0.32 0.37 0.33 0.32 0.30 0.31 0.44 0.41 0.38 0.34 0.32 0.35 s
after 20 s idle:  7.40 s
after 20 s idle:  0.33 s
after 20 s idle:  0.46 s
```

Warm, the API answers in ~350 ms. After a short idle it can take **7–14 s** to
answer the first request. That is a provisioning stall, not a rate limit — a
rate limit would carry 429 and `Retry-After`, and none was seen.

This is also why the failure is non-deterministic: which spec fails changes
every run, individual re-runs often pass, and a file that failed in one round
passes in the next.

## Why these specs and not those

The Dashboard wait is not the same in every file:

| Budget | Specs | Result today |
| ------ | ----- | ------------ |
| 20 s wait | `live-brand-rules`, `live-country`, `live-generate`, `live-knowledge`, `live-proposals`, `live-studio`, `live-wallet` | **below every measured walk (20.3–22.3 s)** — passes only when the country lookup is fast |
| 25 s wait | `live-brand`, `live-notifications`, `live-schedule-repair`, `live-scheduling`, `live-team` | passes unless one call cold-starts |
| no `test.setTimeout` (30 s for the whole test) | `live-auth`, `live-brand`, `live-brand-rules`, `live-team` | **cannot fit** — the walk alone is 27–29 s door to door |

The four specs that failed on `main` in the control run are exactly the ones in
the third row plus the 25 s row: `live-auth`, `live-notifications`,
`live-scheduling`, `live-team`, each on the same locator with the same timeout
as on the M2 branch.

## What the suite needs

Not backoff — there is nothing to back off from; no call is being refused.
In order of how much they fix:

1. **Ward: keep the function warm, or make `PUT /orgs/:id/country` not block
   the response.** 14 s of a 25 s budget for one external lookup leaves no room
   for anything else, and the cold-start tail is what actually pushes it over.
   Provisioned concurrency (or a ping) removes the 7–14 s stalls; making the
   holiday load asynchronous removes the dependency entirely.
2. **Until then, the budgets are wrong, not the app.** The three specs with no
   `test.setTimeout` cannot pass at any wait value, because the walk needs
   ~29 s and the test is capped at 30 s. Raising `test.setTimeout` to 150 s
   (which nine of the thirteen files already do) and the Dashboard wait to
   45 s would make the suite reflect the product again. **Not done here** —
   the brief was to diagnose, and changing a spec's budget to make it pass is
   the kind of edit that should be a deliberate, separate decision.
3. **An allowlist is not the answer.** Every operation returns the documented
   status; there is nothing to allow.
